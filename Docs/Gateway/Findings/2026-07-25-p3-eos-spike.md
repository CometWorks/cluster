# P3 — EOS termination spike (Gateway §12 item 3, Security §10)

Two questions gated EOS work: *does the EOS SDK run in a non-game .NET 10 process on Linux*,
and *what exactly has to be reimplemented to terminate EOS clients at the Gateway*.

## The SDK question: answered, it works

A standalone .NET 10 console process on `polaris`, referencing the game's `EOSSDK.dll` with
`libEOSSDK-Linux-Shipping.so` aliased as `EOSSDK-Shipping.dll` (the managed binding imports
the Windows name):

```
Initialize: Success
PlatformInterface.Create: ok
CreateDeviceId: DuplicateNotAllowed
Connect.Login: Success user=00028ac842134f57af706f4e54b87eb2
```

So platform creation and the dedicated-server Connect login (device-id credential, exactly
what `MyEOSUser` does when `isDedicated`) work outside the game process.

**Trap:** the credential order in `MyEOSService.InitNetworking` is
`(clientId, clientSecret, productId, sandboxId, deploymentId)`. Reading `MyProgram.cs`'s call
site as product/sandbox/deployment-first gives `CreateDeviceId: AccessDenied` with no other
diagnostic. The dedicated server also creates the platform with `IsServer = false`.

## The blocker: the EOS game traffic is not raw EOS P2P

`MyEOSPeer2Peer.SendPacket`/`ReadPacket` do not call the EOS P2P interface directly — they go
through `MyP2PQoSAdapter` (`VRage.EOS/VRage/EOS/MyP2PQoSAdapter.cs`, 1549 lines), a bespoke
reliability/fragmentation/QoS layer SE runs *on top of* EOS P2P because EOS caps a packet at
1170 bytes. Both ends of a vanilla EOS session speak that layer, so a Gateway that terminates
EOS clients must reproduce its wire protocol exactly — ordering, acknowledgement, fragment
reassembly, the reserved channel 200 probes — not merely relay EOS packets.

That is a different class of work from Steam termination, where Valve's SDK owns reliability
and the Gateway only had to mirror ~200 lines of `MySteamGameServer`/`MySteamPeer2Peer`.

## Why it stops here rather than shipping half of it

The method that made the Steam join path trustworthy was golden fixtures generated from the
real serializer (see `2026-07-25-p3-steam-termination.md`). The equivalent for the QoS layer
is captured vanilla EOS traffic — and this bench has no EOS-side client to capture from:
`sirius` has the Steam build and one Steam account, `polaris` has no game client at all.
Publishing an EOS lobby without a working P2P termination would put a browser row in front of
cross-play players that cannot be joined, which is worse than no row.

**Status:** EOS termination is feasible and unblocked at the SDK level; it needs a captured
EOS session (an Xbox/Microsoft Store or Epic client, or a second machine running the retail
client in cross-play mode) to pin `MyP2PQoSAdapter`'s wire format before it can be written
with the same confidence as the Steam path. Everything above it in the Gateway — admission,
identity binding from the validated `userId`, the `ServiceName == "EOS"` binding path on the
node, cluster-wide publishing — is already frontend-agnostic and in place.

## What shipped: `--eos` selects the frontend, login only

Per the 2026-07-25 decision to defer EOS testing but keep the protocol selection in the Gateway,
`--eos [host:port]` starts `EosFrontend`: `PlatformInterface.Initialize`, `Create` with the
dedicated-server credentials in the right order and `IsServer = false`, `CreateDeviceId` +
`Connect.Login` with the device-id credential, and a 50 ms tick pump. Verified inside the Gateway
process on `polaris`:

```
Gateway listening on 127.0.0.1:27116 (dt-debug) 0.0.0.0:27118 (eos, login only), backend …
EOS frontend logged in as 00028ac842134f57af706f4e54b87eb2 for 0.0.0.0:27118 - cross-play
publishing and client termination are not implemented yet (MyP2PQoSAdapter wire format)
```

`EosFrontend.TerminatesClients` is a hard `false` so the relay never guesses, and `--eos` does not
count as a client frontend: a Gateway started with only `--eos` is refused rather than brought up
accepting nobody, and it may not share a port with the Steam or Direct Transport frontend. Those
three rules are pinned in `SelfTest.TestNetworkSecurityOptions`. `/transport/status` reports an
`eos` block with the local user id and `terminatesClients: false`.
