# P3 — Steam termination at the Gateway

Phase 3 (Clustering §13, Gateway §4.2, Security §3) moves the public transport surface into
the Gateway. This records what was verified, what was built, and the traps.

## Spike first: a Steam GameServer inside a non-game .NET 10 process (Gateway §12 item 1)

This gated the whole phase. It **passes** on `polaris`, with no Steam installed:

```
GameServer.Init(0, 27016, 0xFFFF, eServerModeAuthenticationAndSecure, "1.209.024")
→ steamId=90289557627825182 publicIp=5.150.251.169 loggedOn=True secure=True
```

Requirements, all satisfiable outside the game process:

- `Steamworks.NET.dll` + `libsteam_api.so` from the Gateway's `Native/`, plus the
  `steam_api64_shim.c` shim compiled to `libsteam_api64.so` (Steamworks.NET imports
  `steam_api64`; the shim forwards the renamed `SteamInternal_GameServer_Init` to `_V2`).
- `steamclient.so` staged at `~/.steam/sdk64/steamclient.so` — the loader looks there when
  no Steam client is installed. The Gateway stages it from its own output directory, the
  same bootstrap `MyProgram.InstallBundledSteamClient` does.
- **`SteamAppId` must be exported through `setenv`, not `Environment.SetEnvironmentVariable`.**
  .NET keeps a managed copy of the environment on Unix, so the native SDK never sees a
  managed set and `GameServer.Init` returns false with no diagnostic beyond the
  `steamclient.so` load line. This is the root cause of the 2026-07-07 finding
  ("the Steam server path still fails after loading steamclient.so, so EOS is the verified
  startup path") — it was never a Linux limitation.

A2S from a second host on the LAN answers with the full info reply (server name, map,
folder, game, version, server SteamID), so the query surface works cross-host.

## What the Gateway now does

- `--steam [host:port]` starts `SteamFrontend`: GameServer identity in VAC-secure mode,
  `LogOnAnonymous` + `SetAdvertiseServerActive`, the master-server query socket on the game
  port, and GameServer P2P termination on the vanilla channels {0, 2}.
- Auth tickets ride inside `CLIENT_CONNECTED`; the session sits in `TicketPending` with **no
  node attached** until `ValidateAuthTicketResponse` says OK and the §3.4 config gate passes.
  Rejections synthesize `JOIN_RESULT{reason}` at the Gateway — nothing the client sent is
  ever flushed to a node, because a rejected session never attaches and the relay path only
  drains `ClientBacklog` on attach.
- A later non-OK verdict for an admitted client is a revocation and disconnects only that
  client (`ticket-revoked-<reason>`); `EndAuthSession` fires on teardown.
- Browser publishing is Gateway-owned: real cluster-wide player list and count (the vanilla
  per-node "chat bot" member is **not** reproduced), world name, cap, and the vanilla tag
  string `groupId… version… datahash… mods… gamemode… view… modsTotalSize…`. An accept-all
  cluster additionally publishes ` acceptall1` so it is never silently public.

## Traps found

1. **VRage serializes struct members alphabetically, not in declaration order.**
   `MySerializerObject` takes its member list from `TypeExtensions.GetDataMembers`, which
   sorts by `DeclaringType.Name + MemberName`. `ConnectedClientDataMsg` is therefore
   `ClientId, ExperimentalMode, IsAdmin, IsProfiling, Join, Name, ServiceName, Token`, and
   `JoinResultMsg` is `Admin, JoinResult, ServerExperimental`. Decoding in declaration order
   yields plausible-looking garbage. The golden fixtures in `SelfTest` are generated by the
   real serializer and pin this.
2. **The last byte of a vanilla message carries uninitialized padding bits.** `BitStream`
   sizes a packet as `ceil(bits/8)` and never clears the tail, so two runs of the same
   message can differ in the final byte. Frame comparisons mask it off.
3. **The A2S query socket and a Direct Transport frontend cannot share a port.** The Gateway
   refuses that configuration at startup rather than failing to bind at random.

## Direct Transport on the public port is now a debug option

`--dt-debug` (default off) keeps the Phase 1/2 accept-all frontend for development and the
test lanes. Security §3.6's guardrail is enforced at startup: it requires
`CLUSTER_ALLOW_TEST_ACCEPT_ALL=true`, refuses a publicly reachable bind address, refuses
to share a public interface with the Steam frontend, logs a loud warning, and tags the
browser row. With no frontend enabled at all the Gateway refuses to start.

## Intra-cluster link security

The node⇄Gateway Direct Transport link authenticated cluster membership with a *constant*
string (`SE-ClusterNodeLink-v2`), so anything that could reach a node's DT port could attach
arbitrary clients to it. The handshake now carries the registry-issued join token
(Security §4.1/§4.3), validated on the node with a constant-time hash compare against the
current and previous tokens, fail-closed.

## Closed question: password worlds need nothing from the Gateway (Gateway §12 item 5)

The open item was whether `ServerPasswordSalt` derivation is stable across serving nodes, or
whether password handling has to be pinned to one node. It is stable, by construction:

- `MyDedicatedServerBase` flips `IsPasswordProtected` only when the node's config carries *both*
  `ServerPasswordHash` and `ServerPasswordSalt`, and both are plain config strings
  (`MyConfigDedicated`) — nothing in the flow is derived from the node, the session or the ticket.
- The salt reaches the client verbatim in the serving node's `ServerDataMsg`; the client derives
  `Rfc2898DeriveBytes(password, salt, 10000).GetBytes(20)` and `OnPasswordHash` byte-compares that
  against the configured hash, with 3 tries before a kick.
- The cluster already requires identical node config (Security §3.4 config hash), so every node
  answers with the same salt and accepts the same hash. A forced reconnect restarts the whole join
  against another node and re-validates with the same numbers.

So the split stays as the plan has it: the password flows node-side over relayed channels 0/2, and
the Gateway's only part is advertising the flag in the browser row (`SetPasswordProtected`, from
`AdmissionSettings.PasswordProtected`). No Gateway-side hash, salt or `PasswordRequired`
synthesis — and no cluster-specific plumbing, since the operator sets the pair in each node's
`SpaceEngineers-Dedicated.cfg`. P3-PUB-05's remaining value is the live re-validation check, which
needs a client that can answer the password prompt; it is not automated yet.

## Resolved: an immediate rejoin died in the Steam session the Gateway had just closed

The symptom was a rejoin right after a forced disconnect never delivering `CLIENT_CONNECTED`:

```
Accepted client <id> from steam:<id>
Accepted Steam P2P session with <id>
Client <id> disconnected: steam-session-failed: k_EP2PSessionErrorTimeout
```

Two experiments separated it from the ban that first exposed it. The node-crash leg force-
disconnects the same client (`node-link-lost`) and its rejoin, minutes later, is admitted on the
first attempt; the ban leg's rejoin, five seconds later, failed the same way twice. So the variable
is *how soon* the client comes back, not why it was dropped.

The mechanism, read off the Gateway log rather than guessed:

1. The player's client exits. Steam tells the GameServer by sending a **second**
   `ValidateAuthTicketResponse`, `AuthTicketCanceled`, for the session that is going away.
2. The Gateway correctly treats a post-admission verdict as a revocation (§2.6) and drops the
   session — and, as it was written, called `CloseP2PSessionWithUser` in the same breath.
3. The relaunched client sends its first packet into that closing session. It is lost, no new
   session request fires for it, and the join dies on Steam's own timeout with the client sitting
   at "Server responded" until it gives up.

Fix: a detached session now keeps its Steam P2P session for a 30 s **rejoin grace** —
`EndAuthSession` only — and inbound traffic re-adopts it. Because no session request fires inside a
live session, the first packet of the new join is what opens the client session
(`OnSteamPacket`), and the ticket in it still has to validate before any node sees the client. The
pump hard-closes whatever nobody came back to.

What the grace buys is *not* only the adopted session — the client takes a minute to restart, so it
usually returns after the reap — it is that the close no longer collides with Steam's own
processing of the cancelled ticket. Closing the session in the same breath as that callback left
the user's server-side state unusable for the next attempt; deferring it lets Steam settle, and the
returning client's session request is then answered cleanly.

Verified with the retail client: rejoins five seconds after a forced disconnect are admitted on
attempt 1, 3 for 3 (the revocation leg twice, the ban leg once), where the same pattern failed 0 for
2 before. The banned rejoin is now refused with a real `JOIN_RESULT{BannedByAdmins}` instead of a
silent timeout, so the lane asserts that reason strictly.

Two more defects surfaced in the same log and are fixed with it:

- **A pending join was aged out of its own backlog.** `client-backlog-expired` fires when the client
  backlog is older than 10 s, but a session waiting for its ticket verdict has nowhere to flush to
  by design (§3.2 attaches no node before admission), so the age was measuring the Steam round trip.
  It cost a rejoin its first attempt in a real run. The age rule now applies only to admitted
  sessions; the size cap and overflow drop still bound the memory.
- **The armed test verdict was consumed by the cancellation callback**, not the next join, so the
  fed rejection paths tested the revocation branch by accident. The armed verdict lives in the
  Gateway now and applies only to a session that has no credential yet.

## The lane: what it proves, and the three test bugs that looked like product bugs

`TEST_PATH=steam` (`Test/steam_lane.py`, driven by the bash harness after the cluster and the local
Direct Transport debug client are playing) does this with the retail client on `sirius`:

1. A2S info query from `sirius` answers with the configured server name, and `/transport/status`
   carries a real GameServer identity — the browser row works cross-host (P3-PUB-01).
2. The client joins over real Steam P2P: `Accepted Steam P2P session` → `Steam ticket verdict … OK`
   → `Admitted Steam client … name 'Viktor'` → node link → World Authority identity bound from the
   *validated* userId, then it spawns a living character.
3. The cluster-wide player list on the other node carries both frontends' clients with that
   identity — one world, two transports.
4. Its own partition is handed to the other node and it keeps playing (P3-PUB-02).
5. The node serving it is SIGKILLed and never restarted: the dead node's ownership drains from the
   registry, everything reappears on the survivor, and the client rejoins and plays again *under the
   same World Authority identity* (P3-PUB-02's node-crash and reconnect half).
6. A verdict injected after admission revokes the ticket: that client alone is dropped, the Direct
   Transport client keeps playing, and a fresh ticket gets it back in (P3-AUT-02).
7. `VACBanned`, `TicketAlreadyUsed` and `NoLicenseOrExpired` are fed to the next real validation in
   turn: each join is refused at the perimeter with that reason and no node ever sees the client
   (P3-AUT-01 — the remaining verdicts are pinned by the self-test's mapping table, since Steam
   issues none of them on demand).
8. Banned mid-session: force-reconnected, and the rejoin is refused with a synthesized
   `JOIN_RESULT{BannedByAdmins}` before any node sees it (P3-AUT-03/04).

Three failures along the way were the test, not the product, and each cost a full bring-up:

- **The refresh sweep raced the ticket.** This one *was* a product bug and the lane found it:
  `BeginPlayerAdmission` ran for a session still in `TicketPending`, from the periodic World
  Authority refresh, and killed the join with "Client has no validated credential". Fixed by
  requiring a validated credential at every admission entry point.
- **A guessed response shape.** The lane asserted `.Players[].SteamId`; `/cluster/online-players`
  actually answers `{node, local[], cluster[]}` with `steamId`/`identityId`. jq evaluated it to
  false and it read exactly like a replication failure.
- **A handover the Gateway cannot do.** Both characters spawn at Start, so they share a partition,
  and a multi-client partition handover is deliberately unsupported (the automatic loop logs
  "automatic handover deferred"). The lane now teleports the local client away first. Also: clearing
  the Gateway's `--source-control/--target-control` arguments to stop automatic co-location breaks
  the fenced handover route, which needs those fixed endpoints — `POST /automatic/pause` is the
  right switch.

That is why this lane is Python and the bash harness only brings the processes up (see
`AGENTS.md`): every one of these was a silent false assertion in bash, and the 500 body that finally
named the third cause was being discarded by `curl -f`.

## What this bench cannot do: P3-PUB-04's full transport swap

The plan asks for P1-HND-01/02/04, P1-REC-01/04 and P2-WA-06 to be re-run with *every* headless
client Steam-terminated, assertions unchanged. That needs two simultaneous Steam-terminated clients,
and this bench has one Steam account (`76561198223054696`) on one machine with the game installed
(`sirius`); `polaris` has no Steam at all, and Steam will not run the same game on two accounts at
once. So the multi-client scenarios cannot be transport-swapped here at all — not a scheduling
choice, a licence-count limit.

What is reachable with one Steam client is what the lane does: the client's own partition handed
between nodes with the session riding through (P1-HND shape), the serving node lost and the client
recovered onto the survivor (P1-REC shape), and cross-node routing with the second client on the
Direct Transport frontend, which is the interesting half anyway — the two frontends share one world,
one player list and one identity chain. Closing P3-PUB-04 properly needs a second Steam account and
a second host with the game installed.
